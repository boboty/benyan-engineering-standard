# 测试与验证

使用 pytest，优先覆盖业务规则、边界、状态变化、金额、权限及外部服务失败。核心逻辑验证正常、边界和明确失败路径。Bug 修复尽量先写复现测试。无需为无意义 getter/setter 追求覆盖率。`make check` 执行静态检查与自动测试；smoke/integration 验证需实际启动应用并从 HTTP 边界调用。接口或 UI 适用时须实际调用或操作。

## 验证环境的项目归属

- **项目决定环境**：通用规范只要求可重复、可隔离、可追溯的验证；数据库主机、共享服务、测试账号、允许的本地容器方案和环境例外，由具体项目的 `AGENTS.md` 或项目工程文档明确，不在通用规范硬编码。
- **复用已配置的基础设施**：项目已指定现有开发/验收服务时，优先复用；不得无故另起数据库服务、安装同类服务或擅自切换验证目标。项目可明确选择本地数据库、容器或 Testcontainers，通用规范不强制某一种技术。
- **同服务、数据隔离**：不同开发/验收任务可以使用同一数据库服务，但应按风险使用独立测试库、schema 或等效隔离单元；不得把开发业务库、生产库或其他执行者的数据当作可清理的测试夹具。独立验证不必等于独立部署一套服务。
- **证据与清理**：验证记录应标明环境及版本、数据来源、验证范围和未运行项目；敏感连接信息不进入仓库、日志或证据。只清理能够证明归属本次运行的资源，先保留必要的脱敏证据；清理失败应披露。
- **环境异常不得偷换结论**：默认环境不可用、权限不足或运行方式不兼容时，报告阻塞与已取得的证据。改用其他环境须经项目约定或明确授权，并说明证据差异，不将替代性静态检查冒充数据库集成验证。
- **CI 独立约定**：项目 CI 的隔离数据库或容器机制可与交互式开发环境不同；是否运行全套测试，以风险和项目门禁决定，而不是一律重复启动或重复执行。
