# UI 设计意图与质量验收规范

本规范补充 [共享 Web 前端规范](15-web-frontend.md)，适用于新增、重做或明显调整的可视页面、组件及交互。纯 API、脚本和无可视界面的任务不适用。目标是形成符合业务语境、可用、可访问且有一致设计语言的产品界面，而非单纯追求“看不出 AI 生成”。

## 权威顺序与适用范围

1. 已明确的产品需求、用户任务与验收约束优先。
2. 本仓库 `design-system/` 是品牌、Design Tokens 与已有组件的唯一权威来源。先复用，不复制或覆盖另一套主题。
3. 具体项目已批准的设计稿、视觉方向和 `AGENTS.md` 规则在其范围内生效；偏离通用默认值须记录理由。
4. 外部 UI Skills、组件库、参考站点、审美检查器仅作按需参考，不得自动引入新设计系统、依赖、远程执行脚本或替换已有组件。外部组件须经过许可证、兼容性、可访问性、安全性和维护成本审查。

## 先定义意图，再生成界面

对新增页面或显著改版，在实现前形成简短的 UI Brief；小改动可直接在任务说明中写明：

- **业务与用户**：产品类型、主要用户、核心操作和成功判据；页面为何存在。
- **界面类型**：营销展示页、业务工作台、数据看板、表单流程、管理后台等；不同类型不能套用同一种布局。
- **信息优先级**：首屏最重要的信息、首要操作、次级操作和高风险操作；所用内容必须来自真实业务或明确标记的示例数据。
- **视觉方向**：优先基于现有 Design System 说明布局密度、排版层级、留白节奏、表格/卡片使用边界、图标与动效倾向；不重新发明品牌色。
- **状态与约束**：加载、空数据、错误、成功、无权限、长文本、窄屏以及键盘使用的预期。

若改动只影响单一按钮、标签或微小样式，沿用现有页面设计，无须补写完整 Brief。

## 避免模板化 AI 界面

以下模式不是绝对禁令，但**无业务理由不得默认采用**：

- 与产品无关的紫蓝渐变、炫光、玻璃拟态、背景装饰、悬浮大卡片及全页面统一大圆角；
- 不区分内容关系的“卡片套卡片”、三等分功能卡、每页都放大 Hero、泛化指标和伪造的用户评价；
- 重复使用“智能、高效、赋能、革新”等空泛文案，不说明对象、操作、条件与结果；
- 为视觉效果牺牲扫描效率的数据看板：把适合表格、筛选器、状态列表或明细的内容全部转成卡片；
- 无信息价值的图标、动画、渐变文字、随机插画，以及所有按钮都做悬浮弹跳；
- 同一产品中缺少统一字号层级、间距节奏、组件状态和对齐基线。

判断标准不是“某种颜色、字体或卡片是否出现”，而是：**它是否由真实用户任务、品牌语言与信息结构支撑**。需求或既有 Design System 明确要求的风格不应因“像 AI”而被禁止。

## 实现要求

1. 按 Design Tokens → 既有组件/规则 → 必需的业务组件 → 页面组合实现；优先解决信息架构、层级和交互，再做视觉润色。
2. 业务工作台优先保证信息密度、导航稳定、表单效率、状态可辨和数据可追溯；营销展示页可有更强的叙事与视觉表现，但必须服务真实内容。
3. 文案具体、可操作；不得把假数据、假指标、假客户 Logo 或示例评价表现为事实。
4. 所有交互控件具有真实行为；具备必要的 hover、focus、disabled、loading、empty、error、success 状态。危险操作应有明确后果与适当确认/撤销机制。
5. 保证语义结构、标签、焦点顺序、键盘操作、可辨识的焦点样式、文本对比度；尊重减少动态效果的系统设置。
6. 在目标断点检查布局和长文本，防止遮挡、溢出、横向滚动及关键操作不可达；涉及响应式的变更至少检查窄屏与桌面。
7. 动效只用于反馈、导航连续性或状态变化；不为“高级感”添加持续动画。不要为小型 UI 任务无依据地增加视觉依赖或动画库。

## UI 验收门禁

凡涉及页面可视或交互变化，除既有 lint、typecheck、test、build 和必要的 E2E 外，须以**实际渲染页面**检查，而非仅凭代码推断：

- **业务适配**：真实用户能否迅速找到主要信息和主要操作；是否存在纯装饰或虚构内容；
- **视觉一致性**：是否复用 Design System，排版、密度、对齐、间距、色彩和状态是否一致；
- **交互完整性**：主要路径及加载、空态、错误态、成功反馈是否可用；
- **可访问性与响应式**：键盘、焦点、标签、对比度、窄屏和长文本是否经检查；
- **反模板化复核**：是否存在与业务无关的通用 SaaS Hero、渐变、玻璃、卡片堆叠和空洞营销文案。

对新增页面或显著改版，至少提供桌面与窄屏截图（或等效可复核的浏览器记录），说明发现与修复结果；必要时追加针对交互状态的截图。对仅改微小样式的任务，可将证据范围缩小至变更部位。无法运行浏览器时必须披露未验证项，不得宣称视觉验收通过。

任何影响主流程的交互故障、明显遮挡/溢出、虚假内容、关键可访问性缺陷或明显破坏既有 Design System 的偏离均不得标记为 UI 验收通过；纯审美偏好问题由项目负责人按 UI Brief 判断，不建立统一的审美打分阈值。

## 外部参考（不自动成为规范或依赖）

- [Arc UI](https://uiarc.dev/docs/ai)：组件检索、设计与内容规则、交互/响应式/可访问性参考；
- [Impeccable](https://github.com/pbakaus/impeccable)：设计指导、页面润色、审查与反模式检测；
- [Anthropic frontend-design](https://github.com/anthropics/claude-code/tree/main/plugins/frontend-design)：根据产品语境作出明确视觉选择；
- [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)：交互、可访问性与 Web UI 代码复核；
- [Taste Skill](https://github.com/Leonxlnx/taste-skill)：设计方向探索、实际浏览器截图与迭代；
- [No Slop UI](https://github.com/LeoStehlik/no-slop-ui)：面向业务工作台的克制布局与反模板化检查。

引用第三方规则时记录来源及版本/提交。不得在执行时无审查地拉取可变的远程指令；是否安装由具体项目决定。
